# 计量说明

## 资源归属

- **CPU**：仿真进程树中各进程 `(user + system)` CPU 时间增量之和，除以查询区间墙钟时间与整机逻辑核数。一个核心满载对应 `1 / 核数`。
- **主存**：进程树 RSS（Windows 工作集）之和，除以整机物理内存。共享页可能重复计入，比例最大为 1；报告同时保留原始字节数。
- **GPU**：NVML 进程 SM 利用率，按 PID 与创建时间筛选。每个驱动时间戳内目标进程占用相加并截断至 100%，再对新取得的时间戳求平均。选中多卡时等权平均，任一卡无数据则该次 GPU 聚合值缺失。只在其他 PID 有新鲜样本、目标 PID 没有活动时记录 0。
- **显存**：合并 NVML compute / graphics 进程列表，同一 PID 取最大值，避免重复计算。进程显存不可读时为 `null`，不以整卡显存代替，也不参与 Cres。

默认根进程是调用 Monitor 的进程，可用 `pid` 指定；已发现的子进程被重新挂接后仍跟踪，PID 与创建时间共同识别进程。进程退出或计数不可读时，相应 CPU 区间可能缺失；轮询不能保证捕获采样间创建并退出的短命进程。

同进程中的引擎、渲染、Python 和监控开销均计入。CPU / 主存分母为整机容量，不按容器配额归一化。GPU 设备编号使用 NVML 物理索引，不受 `CUDA_VISIBLE_DEVICES` 重排影响，固定实验推荐使用 UUID。

## 采样与平均值

每次 `advance`、`record_sim_time` 或成功退出 `step` 上下文时同步查询一次；结束时额外查询一次，不增加物理步数。每步必须独立上报，`steps=1`。N 个并行环境在同一时间轴推进一次时，仿真时间只增加一次 dt。

每条记录的占用率代表前一查询结束到本次查询结束的区间，以右端点矩形积分计算：

```text
平均占用率 = Σ(有效区间时长 × 占用率) / Σ有效区间时长
RTF = 墙钟时间 / 仿真时间
Cres = (0.4 × GPU均值 + 0.3 × CPU均值 + 0.3 × 主存均值) × RTF
```

CPU 使用累计计数差，主存是瞬时读数，GPU 有独立的驱动采样窗口，因此均为离散估计。每步查询不保证驱动产生新样本；没有新 GPU 样本时不复用旧值、不补零、不退回整卡数据。日志记录驱动查询游标和取得的样本时间戳。

各资源分别排除缺失区间并使用自己的覆盖时长。全程无有效数据时均值为 `null`，Cres 缺少任一均值时为 `null`。部分覆盖时 Cres 是可用数据估计，可能存在采样偏差；报告保留积分、覆盖时长与 `resource_data_complete`。峰值为有效样本最大值，不是连续时间峰值。

新报告 schema 1.1 使用上述规则；旧 schema 1.0 仍按原来的“完整覆盖才有均值”规则复核，不改写历史数据。旧整机统计不能转换为进程统计。

## 时间与异常边界

墙钟使用 `perf_counter_ns`。初始化、预热、开始同步和报告序列化在计时外；物理循环、循环内渲染、逐步资源查询与日志开销、结束同步均计入。最后一次资源读取完成时停止计时。

异步引擎须自行在每步上报前等待完成。Monitor 的 `synchronize` 回调只在开始前及结束前调用；查询占用率不构成设备同步。

Python 异常与同步失败会保存失败报告。`wall_time_limit_s` 只在结束时判定超时，不强制终止卡死任务。进程强杀或原生崩溃可能只留下部分日志，没有最终报告的运行视为未完成。

## 可选评分与复核

阈值 `rtf_threshold` / `cres_threshold` 默认为 `null`，不生成假定分数。设置阈值 t 后，指标 x 的映射为 `min(1, exp(-(x-t)))`；失败、超时或缺失指标的已配置评分为 0，每项观察点分数为映射值乘 15。

`efficiency_Ec = 0.5 × r_rtf + 0.5 × r_cres`，只表示计算效率维度，不是包含物理一致性与稳定性的综合分。正式评测需统一冻结权重、阈值、采样方式与运行边界。

`verify` 校验原始日志 SHA-256、配置与采样序列，并重算指标和资源汇总。哈希用于发现意外修改，不证明日志未被重新生成，也不验证引擎上报的物理时间真实性。
